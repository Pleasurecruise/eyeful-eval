# 结果

[English](../RESULTS.md)

按 [EVALUATION.md](EVALUATION.md) 的方案得到的结果，eyeful 构建 `61c1b8b`，模型 DeepSeek V4.1 Flash。
区间为对 subject 重抽样的 95% bootstrap 区间；p 值来自 McNemar 精确检验。

## 1. 实施情况

| 基准               | subject | run       | 审查 | 排除：越界读取 | 三次尝试仍失败 |
| ------------------ | ------- | --------- | ---- | -------------- | -------------- |
| SWE-bench Verified | 30      | 150 / 150 | 300  | 5              | 6              |
| Code Review Bench  | 10      | 50 / 50   | 150  | 1              | 6              |

被排除的审查读取的都是仓库外的库源码，没有一个读到评测数据。SWE-bench 上停用只读条件之前完成的 6 个 read_only 审查保留但不分析。失败的审查视为什么都没检出。SWE-bench 的修复由官方 harness（`swebench==5.0.2`）评分，Code Review Bench 由其自带 judge 评分，每条审查都无错误地评完。对方案的偏离见 [amendments.md](../../registry/amendments.md)。

## 2. RQ3：检出，含 planner 消融（RQ1）

| 配置                         | SWE-bench 召回率（30 个缺陷） | Code Review Bench 召回率（25 个 Core 缺陷） |
| ---------------------------- | ----------------------------- | ------------------------------------------- |
| panel，一次                  | 0.73 [0.57, 0.87]             | 0.72 [0.52, 0.90]                           |
| single，第一次               | 0.70 [0.53, 0.87]             | 0.72 [0.60, 0.86]                           |
| single，三次中任一次         | 0.83 [0.70, 0.97]             | 0.80 [0.67, 0.92]                           |
| fixed（planner 消融），一次  | 0.77 [0.60, 0.90]             | 0.76 [0.62, 0.89]                           |

| 配对（仅前者检出 : 仅后者检出） | SWE-bench     | Code Review Bench |
| ------------------------------- | ------------- | ----------------- |
| panel 对 single 第一次          | 2 : 1，p=1.00 | 2 : 2，p=1.00     |
| panel 对 single 三次中任一次    | 0 : 3，p=0.25 | 1 : 3，p=0.63     |
| panel 对 fixed                  | 2 : 3，p=1.00 | 2 : 3，p=1.00     |

所有差异均不显著。panel 没有比同一模型、同样 skill 的单个 agent 检出更多缺陷，planner 也没有比两个固定专家检出更多。single 跑三次的成本与 panel 跑一次相近，召回率在两个基准上都最高，但同样不显著。Code Review Bench 上 panel 和 single 在 8 个 Core 类别中的 5 个检出缺陷，fixed 为 6 个。

## 3. RQ3：噪声（Code Review Bench）

| 配置   | 每次报出，none    | 精确率，none      | 精确率，read_only | read_only − none    |
| ------ | ----------------- | ----------------- | ----------------- | ------------------- |
| panel  | 16.0 [12.9, 19.1] | 0.14 [0.09, 0.19] | 0.16 [0.12, 0.21] | +0.02 [0.01, 0.04]  |
| single | 5.7 [4.5, 6.9]    | 0.37 [0.26, 0.48] | 0.36 [0.25, 0.47] | −0.01 [−0.05, 0.03] |
| fixed  | 6.1 [4.9, 7.3]    | 0.39 [0.26, 0.54] | 0.41 [0.26, 0.55] | +0.01 [−0.02, 0.04] |

只读 judge 约拦下十分之一的 finding，精确率最多提高 2 个百分点。配置之间的差别更大：panel 报出的 finding 接近 single 的 3 倍，精确率却不到其一半。这些 Java subject 上无法执行测试，execution 在此等同于 read_only，因此执行验证能否降噪没有被测量。

## 4. RQ2：可验证性，含 oracle 规则消融（SWE-bench）

| 指标                                     | 值                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| 执行过的 finding                         | 154                                                                    |
| 走完全部六道关卡                         | 0.76 [0.61, 0.88]                                                      |
| 其余停在哪一关                           | pass_to_pass 19，introduced 11，fail_to_pass 4，fails_as_claimed 2，not_flaky 1 |
| 被复现 finding 的 oracle                 | derived 129，implicit 9，specified 2                                   |
| 按 oracle 规则可阻塞；其修复解决原题的比例 | 11；0.27                                                             |
| 消融：任何复现都可阻塞时；其修复解决原题的比例 | 140；0.64                                                              |
| 验证损失                                 | 按定义为 0（方案 §8）                                                  |

四分之三的 finding 带有一个测试：在改动上失败、打上修复后通过，且回归套件仍然通过。oracle 几乎都从代码本身推出，所以按 oracle 规则能阻塞的 finding 很少；若允许任何复现都阻塞，数量升到 140，其中 64% 的修复解决了原题。

## 5. RQ3：成本

每次审查的均值，execution 条件（括号内为 none）。

| 配置   | SWE-bench token（千） | SWE-bench 美元 | Code Review Bench token（千） | Code Review Bench 美元 |
| ------ | --------------------- | -------------- | ----------------------------- | ---------------------- |
| panel  | 401 (272)             | 0.12 (0.09)    | 1177 (869)                    | 0.37 (0.28)            |
| single | 181 (113)             | 0.05 (0.03)    | 354 (260)                     | 0.12 (0.09)            |
| fixed  | 307 (210)             | 0.09 (0.07)    | 597 (428)                     | 0.20 (0.15)            |

panel 的成本是 single 一次的 2.2 到 3.3 倍。执行使 SWE-bench 上每次审查的成本增加 45–60%，Code Review Bench 上约 36%，只读 judge 的成本与之相当。

## 6. 结论

1. **规划没有提高检出（RQ1、RQ3）。** 规划出的 panel 没有比单个 agent 检出更多缺陷，planner 也没有比两个固定专家检出更多。重复运行单个 agent 的召回率比两者都高，但不显著。
2. **只读验证没有降低噪声（RQ3）。** 与审查者同一模型的 judge 拦下的 finding 很少，精确率几乎不变；panel 的精确率不到 single 的一半。验证只会删去 finding，不可能提高召回。
3. **执行的贡献在于证据（RQ2）。** 四分之三经执行的 finding 附带可复现的测试和经验证的修复，但预期行为很少来自代码之外，所以只有 11 条 finding 可以阻塞改动。

这些都是同一模型下的内部比较，subject 只有 30 个和 10 个：没有显著差异不等于等价，方案 §8 的有效性威胁同样适用。执行验证（而非只读 judge）能否降噪没有被测量。ReviewBench 是开发中未用过的留出集，将于 2027 年 2 月运行，检验这些结论是否成立（[计划](../../registry/reviewbench/plan.md)）。
